# v0.8.2 ホーム・ごみ箱と変更履歴

## 症状と不足していた処理

ユーザー報告では、アプリの2作品はMEGAのごみ箱に移したPromptGallery内にあり、ホーム側にある同名フォルダの作品は表示されない。

v0.8の再構築は「受け取ったf一覧」の親子関係を直すものだった。一方でkeepalive:falseのため、その一覧のsn以降にある変更履歴を適用していなかった。公式Webクライアントは初期表示前に履歴を取得する。したがって、古いスナップショットでホームにあったフォルダが表示され続けるケースが残る。

これは公式実装と同形の「過去の一覧＋移動・追加の変更パケット」で再現したもの。ユーザーの実際のAPI応答や実アカウントの復旧は未観測であり、実環境の原因を確定済みとは扱わない。

## 実装

- 全体取得を公式クライアントと同じa:f,c:1,r:1に合わせ、caによるキャッシュ利用を指定しない。
- f応答のsnからscを読み、追加(t)、移動(d/t)、削除(d)、属性更新(u)を一時的なノードマップへ反映。
- 待機URL(w)を受け取るまで変更履歴を読み、そのURLへ長時間の待機リクエストは送らない。
- 変更履歴は最大30ページ・合計30秒。取得失敗、制限、更新位置なし、終端未確認は同期失敗として前のツリーを保持。確認できていない古い一覧を新しい同期成功として表示しない。
- 終端確認後にSDKで復号・ノード化し、親子関係を再構築。ROOT型2とRUBBISH型4を検証。
- 読み取り・保存先探索・削除でホーム配下を確認。ごみ箱型4・ごみ箱配下を除外。ホームとごみ箱の間で作品を自動移動・復元・消去しない。
- 診断へ変更履歴の終端確認と反映件数を追加。ID・URL・認証情報は診断へ出さない。

スコープは本アプリのホーム直下PromptGallery/records。共有フォルダの権限・共有鍵管理やバックアップ領域をギャラリーとして扱う機能は追加しない。

## 根拠

[MEGA公式Webクライアント js/mega.js](https://github.com/meganz/webclient/blob/master/js/mega.js)のfetchfmは初期表示前の履歴取得を指示し、f,c:1,r:1で一覧を要求する。[公式SDKのノード種類](https://github.com/meganz/sdk/blob/master/include/mega/types.h)でもホームとごみ箱は区別される。

MEGAJS1.3.10のapi.pull()はsc応答のaを処理し、snで続行、wで待機する。今回の処理は一回の更新を最後まで完了させるため、wで終了する。

## 検証

実SDKを用いて古いホームのノード→ごみ箱移動、新規ホーム側ノード、順不同の子、更新・削除、制限エラー、ページ上限を検証。ブラウザでは同名フォルダがホームとごみ箱にある状態から、ホーム側だけの表示・再取得・削除・新規保存を確認する。既存の制作UIと生成文は変更しない。
